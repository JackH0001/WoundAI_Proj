# 端上路徑 vs 後端路徑：能力差異、前置條件與風險

> 2026-08-04。觸發：實體裝置驗證時發現「端上 ONNX 模型」被列為待驗項目，
> 需要先釐清它現在到底能不能用、以及啟用它會發生什麼事。
>
> **結論先講：端上路徑目前算不出面積，而且在剛實測過的那張影像上會完全失效。
> 現階段不應啟用。** 證據見 §2。

---

## 1. 兩條路徑是什麼

| | 端上（on-device） | 後端（Cloud Run） |
|---|---|---|
| 觸發 | `MeasureViewModel.analyze()` | `analyzeViaBackend()` |
| 分割模型 | `student_fp16.onnx`（assets，13.3 MB） | student → 難例自動升級 A∪U 集成 |
| 尺度校正 | `ArucoDetector`（**stub**） | 伺服器端 `aruco_calibrate` |
| 組織分類 | `computeTissueFrac`（簡化版） | tissue v2（WB + HSV） |
| 模擬圖色彩分割 | 無 | `seg=color` 決定性 HSV |
| 飛輪影像綁定 | **無 `image_id`** → 送標註會被擋 | 有，可送訓練標註 |
| 需要網路 | 否 | 是 |

## 2. 為什麼現在不能啟用（兩個獨立的阻擋理由）

### 2.1 ArUco 是 stub —— 端上永遠算不出 cm²

```kotlin
// ArucoDetector.kt
class ArucoDetector(dictId: Int = 0) {
    /** stub:一律回 null(未偵測)。 */
    fun detect(bitmap: Bitmap, wantId: Int = 7): FloatArray? = null
}
```

`WoundAnalyzer.run()` 的 `markerPxArea = markerCorners?.let { quadPxArea(it) }` 因此永遠是 null，
面積計算的分母不存在 → **`areaCm2` 永遠是 null**。

端上做得出遮罩，做不出面積。而**面積就是整個臨床產出** —— 傷口變大還是變小、癒合率、
PUSH 面積子分，全都建立在它上面。一條算不出面積的量測路徑，臨床上等於沒有。

**根因**：`ArucoDetector` 需要 OpenCV 4.7+ 的 `org.opencv.objdetect.ArucoDetector`，
而專案用的是 `com.quickbirdstudios:opencv:4.5.3.0`（mavenCentral 上 `org.opencv:opencv`
從 4.9 才開始發佈）。這不是「忘了寫」，是相依版本的限制。

### 2.2 student 單獨跑會漏掉真實傷口 —— 而端上沒有集成可以救

2026-08-04 實體裝置實測，範例貼紙傷口照：

| 欄位 | 值 |
|---|---|
| 路由 | `cloud_escalated(AU)` |
| 面積 | 12.05 cm² |
| 信心 | 100% |
| 組織 | 肉芽 72% |

`route` 是 `cloud_escalated(AU)` 代表**student 回了空遮罩**，是 A∪U 集成把傷口救回來的
（後端 `phantom_hint` 也因此被觸發——那個提示的邏輯錯誤已另行修正）。

**端上跑的就是 student。** 同一張影像在端上會是「AI 沒偵測到傷口」，
而端上路徑沒有網路時也拿不到集成。醫師會看到一個空結果，然後從零手畫——
或者更糟，以為這張拍壞了而重拍。

這一項比 §2.1 更根本：就算把 ArUco 補齊，端上的分割品質仍然是這個樣子。

### 2.3 次要缺口

- 組織 v2（WB+HSV）在端上是簡化版，`WoundAnalyzer` 註解仍標 TODO
- 端上無 `image_id` → 產生的標註是孤兒 GT，送不進飛輪（已有守門擋下，不會靜默失敗）
- 模擬圖的色彩分割只有後端有

## 3. 端上路徑真正的價值（不是現在，但是真的）

**離線可用**是唯一但重要的理由：病房 Wi-Fi 不穩、換藥車推到走廊、院內網路政策不放行外部連線——
這些在實務上都會發生，而那時候後端路徑等於整個功能不能用。

其次是**延遲**（省掉上傳往返）與**PHI 不出裝置**（雖然目前上傳的已是去識別影像）。

所以這條路徑不該砍掉，只是**順序在後面**。

---

## 4. 啟用端上需要什麼（依序）

| # | 前置 | 為什麼是這個順序 | 風險 |
|---|---|---|---|
| 1 | **student 模型變強** | 這是根本。模型漏檢時，補再多周邊功能也只是把一個空結果包裝得比較漂亮 | 需要 n=20 收案 → 重訓 → golden 驗證 |
| 2 | OpenCV 升到 4.9+，拿回真 ArUco | 沒有它就沒有 cm² | **會動到原生相依**。AGP/Kotlin/Gradle 組合剛穩定（wrapper 釘 8.13），升版有實際建置風險 |
| 3 | 端上組織 v2 | PUSH 的組織子分需要它 | 中等，純 Kotlin |
| 4 | 原生庫可用性驗證 | `libonnxruntime.so` 在部分 ABI/16KB 分頁裝置不相容，載入拋 `UnsatisfiedLinkError`（**是 Error 不是 Exception，攔不到**）→ App 直接閃退 | 未知，需真機逐台測 |

**第 4 項是目前完全未知的**。App 之所以不自動載入端上模型，正是為了避開這個閃退，
所以「你那台真機到底載不載得起來」從來沒有被驗證過。

---

## 5. 建議

**現階段維持現狀**（端上不自動載入），把時間放在 n=20 臨床收案。理由：

1. 收案本來就是關鍵路徑，其他都在等它
2. 收完重訓後，student 才可能好到值得上端
3. 屆時 OpenCV 升版可以和模型更新一起做，一次承擔一次建置風險

**收案完成後**，建議的第一步是加一個**端上自我檢測**（設定頁按鈕：載入模型 → 跑一次推論 →
回報成功與延遲），而不是直接開自動載入。理由是它回答第 4 項那個未知，
而且失敗時只會顯示一行紅字，不會讓醫師在病房裡遇到閃退。

---

## 6. 給 IRB / 資安審查的說法

若被問到「模型跑在哪裡」，目前的正確答案是：

> 影像分析在**境內雲端**（GCP asia-east1 彰化）執行。行動裝置僅負責擷取影像、
> 顯示結果與醫師修邊確認，**個資（姓名、病歷號）以裝置金鑰加密後永不離開裝置**，
> 上傳的僅為去識別影像與 `WD-` 代碼。
> 裝置端另備有輕量分割模型作為離線備援，**目前未啟用**，啟用前將另行驗證。

最後一句要寫進去——日後啟用時審查者才不會覺得是偷改架構。
