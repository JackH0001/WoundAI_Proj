## 為什麼第二次出現「登入失敗」

Cloud Run 在 15:10:30、15:19:09 對登入請求回覆 HTTP 429，平台原因明確為沒有可用執行個體。候選 revision `woundai-backend-mmhps20261007-cb7f9dc2b28bc` 設定 min=0、max=1、concurrency=1。這兩次不是帳密錯誤證據。

本次日誌中七次 classify 均 HTTP 200，服務端請求時間約 16.9–20.0 秒；近期成功登入約 8.2–13.1 秒。這些是各請求延遲，不是純模型耗時，也不能把等待全部歸因於冷啟動。使用者等待前筆上傳完成後成功三筆，與同時請求容量不足的解釋一致；沒有證明每次失敗都由同一原因造成。

## 33 版修正

- 同一 Google 工作階段共用的 IAP transport 依序送出請求，涵蓋量測、設定與研究待傳。Swift actor 在網路 await 時可重入，因此明確加入排隊；取消移除等待工作，登出使待送工作失效，不自動重送寫入。
- 帳密已儲存與已驗證分開顯示；只在已驗證時顯示 WoundAI 登出。重新進設定會驗證已儲存帳密，按一次「儲存並登入」即可；健康度讀取不抹除成功登入。
- 更換帳號或後端位址不能沿用舊密碼。Google 與 WoundAI 登出仍按既有機構政策連動，不把清除帳密誤呈現為已有成功登入。
- HTTP 429 顯示服務忙碌／請求過於頻繁；401、403、其他錯誤各自顯示，保留 Google 入口錯誤，不再全部誤報密碼錯誤。
- 量測顯示等待秒數及登入、影像準備、保存授權、傳送／辨識／保存的耗時。研究待傳與量測分析分開呈現。
- 新拍攝開始即清除上一筆的畫面結果與修邊確認，作廢舊深度計算回呼；登入失敗不得把上一筆結果當成本次結果。重複操作在分析／存檔期間被擋下。

此版沒有降低模型計算成本、持久保存 Google token，或證明多裝置同時使用不會遇到 429。App 重啟或 Google 驗證失效仍可能需要重新登入。雲端資源維持原省成本配置。
