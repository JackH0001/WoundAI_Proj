# WoundAILite 個人辨識忙碌時的續傳

個人服務的候選映像以一個 Gunicorn worker、兩個 HTTP 執行緒運行。兩筆不同的辨識同時進入影像解碼或模型運算時，兩個執行緒都可能被占用。挑戰碼雖有獨立的撤回請求額度，仍需等執行緒空出才能處理。

每個服務程序現在同時最多讓一筆新的工作進行解碼與推論。另一筆已預留的工作收到 HTTP 429、`lite_model_busy` 及 `Retry-After: 5`，保留原照片、operation 和預留額度。41 版可沿用既有忙碌提示及原工作核對流程。等待本身不會執行模型或結算成功次數。已在執行的工作回報待確認，已完成的工作仍可讀回。

運算中斷後釋放程序內的名額，其他工作可以繼續。已取得執行權且結果不明的工作依原收據保持待確認，避免重跑。跨實例的去重仍由持久化帳本負責。

本機測試使用合成身分與照片。這項限制為模型工作留下處理狀態及帳號請求的空間；網路、請求佇列或儲存服務仍可能延遲回覆。正式容量及撤回延遲需使用實際服務設定量測。研究媒體的撤回在獨立研究服務進行。

### 撤回與刪帳的保留容量

裝置要求撤回驗證時，金鑰識別碼須符合既有的 32 位元組格式。撤回、刪帳與刪帳身分連結請求則先檢查有大小上限的本文、簽章標頭與兩個請求識別碼。明顯不合格式的請求計入一般服務容量。格式通過後仍由原有裝置簽章、計數器及一次性挑戰驗證授權。服務的請求容量與使用者每日免費或 Plus 的成功辨識額度各自計算。

撤回挑戰須確認是現有裝置、仍可發出挑戰，才占用保留容量。簽署的撤回、刪帳或身分連結則在簽章核對後、更新計數器與消耗挑戰之前，以原子方式取得名額。競爭重試共用同一份名額；若名額剛好被其他裝置取得，回覆會附等待時間，原挑戰及計數器可續用。未登記、無效簽章或重送已消耗的挑戰，都不能耗用保留名額。

本機 HTTP 對照使用四個同時連線，混合送出 32 個錯誤請求，再由原裝置簽署撤回。不同組別分別涵蓋缺少簽章、金鑰格式不符及格式正確但未登記等情況。驗證使用合成裝置；實際入口的延遲與費用仍待量測。正式對外服務前，還須限制送進驗證層的請求速率。判斷陌生金鑰可能需要讀取裝置狀態；核對簽章與讀取容量帳本本身也會耗用資源。
