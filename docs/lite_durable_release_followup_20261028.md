# Lite：將切換觀察與日常服務授權分開

日期：2026-10-28。基底 `925e953`；本輪為預設關閉的候選，不是部署或實機驗收。
處理 Claude 對 `9edbda8` 的第一項上市阻擋：31秒 observer 依賴。
沒有更改15分鐘登入期限、App刪帳、token撤銷、訂閱價格或研究同意。

## 修正前與修正後

原生訂閱／新帳號流程，及額度 admission，原本每次都核對短效觀察；前者的
簽章有效期最多30秒，後者同步呼叫 provider。供應端短暫不可用時，連已完成
切換、同一政策的原使用者都不能建立新工作。這個拒絕本身符合舊安全設計，
但不適合作為長期服務可用性的唯一依據。

新增 `lite_service_release.py`：

- 明確發布一份耐久服務狀態，固定來源、映像、穩定帳號scope、政策及其啟用
  起源、額度namespace／切換計畫與共同writer fence。**不延長observer簽章期限。**
- 發布、恢復及升級需要獨立operator簽章，綁定當前狀態雜湊。第一次發布先核對
  每個政策的既有啟用稽核、即時觀察、已停止的舊writer、排空及額度切換回執。
  原訂閱批次與額度切換仍各自要求即時證據；沒有把遷移驗證取消。
- 日常新工作讀取耐久active／paused世代與確認稽核；不讀短效observer，不快取
  allow，不以不明狀態降級成免費。控制或稽核儲存無法讀取時拒絕新工作。
- 控制器與讀取器分開：日常讀取器只有GET用途；控制器沒有顧客HTTP入口。
  簽署發布、暫停、恢復、確認失敗回執及已暫停版本的升級均有明確API。
- 訂閱及額度各留一個不可隨失敗刪除的綁定標記；移除新的reader注入，不能
  自動回到舊observer放行路徑。新來源升級後，舊來源reader拒絕新工作。
- 外部監看發現「觀察不到」只報警；看到符合格式且可驗證的矛盾則CAS停用。
  一條觀察過期不會掩蓋另一條已確認矛盾。修復provider後也不自動恢復：
  需新簽署、精確paused世代及新即時證據。

沒有清空帳號、額度、結果、原影像、研究紀錄或舊稽核。已開始的辨識仍可完成
一次並取得原回執；同一操作重送不再呼叫模型，也不新增扣額度。停止收新工作
與取消已開始工作是兩件事。所有控制資料與研究資料分開。

## 合成驗證與可重跑參照

`test_lite_service_release.py` 用同一套案例跑SQLite與GCS adapter／FakeBucket；
後者驗證generation CAS及故障行為，**不是對Google雲端桶實測**。帳號與Apple
簽章資料為測試生成。`lite_service_release_probe.py` 使用實際ServiceOperations、
JPEG decode及合成模型，前後比較：

| 情境 | 舊路徑 | 顯式啟用本輪候選後 |
|---|---|---|
| 觀察31秒未更新 | 新工作拒絕 | 不使用此期限作日常服務授權 |
| 觀察48小時未更新、跨UTC日 | 沒有進行新請求 | 正常準備／完成，同ID重送模型1次、扣1次 |
| 明確停用，另一個實例 | — | 新工作拒絕；舊結果／回執可讀 |
| 失敗回覆／確認稽核遺失 | — | 相同意圖恢復，不增加世代或重置帳本 |
| 新批次中斷 | — | 只攔該批次帳號，原批次可用 |
| 觀察矛盾／資料庫不可讀 | — | 矛盾停用；資料庫不可讀拒絕，沒有快取放行 |

本機指令（先安裝專案測試依賴，無須雲端憑證）：

```text
PYTHONPATH=tools:engineering/phase2:Backend/Flask:. python -m unittest -v test_lite_service_release test_lite_service_release_probe
PYTHONPATH=tools:engineering/phase2:Backend/Flask:. python tools/lite_service_release_probe.py --output release-probe.json
```

Windows請以PowerShell設定同一PYTHONPATH，分隔符改為分號。覆核包另有可攜
`verify_packet.py`，先只核對檔案雜湊及測試證據，確認內容後再重跑測試。
完整Lite與prelaunch集合重疊，不能加總。最新測試數據以本輪驗證報告為準。
沒有iOS/Android檔案改動，沿用既有925e953 CI證據，**不宣稱本輪重跑原生測試**。

## 同輪發現的雙裝置登入競爭

完整測試曾有一項間歇失敗：先讀到「intent不存在」後，另一請求可能完成同一
intent及stable pointer；原請求卻沿用舊的None，報`missing committed intent`。
三項可控交錯測試在修正前全部失敗。修正只在已看到相同completion／pointer時
重新讀回一次該immutable intent，仍核對原authorization；真的缺資料或授權不符
照樣拒絕。沒有增加Apple查詢、重建帳號、改token或重置額度。

最終本機結果：完整Lite **1,207項通過**；prelaunch **1,175項通過、19個驗證步驟**；
新耐久release **79項**及確定性競爭 **3項**包含於上述集合。另將既有雙裝置
同帳號競爭案例獨立重跑50次全部通過，不加入不同測試項目總數。
首輪5項loopback被沙箱阻擋，允許本機127.0.0.1後通過；後續發現的intent競爭
已保留失敗日誌與修正前探針，不以單純重跑掩蓋失敗。

這些是本機結果；新commit尚未推送，不能宣稱新來源的GitHub CI已通過。

## 不能省略的正式接線與運維條件

1. **舊writer真正被隔離**：簽章觀察只是證明，不能取代IAM、路由與舊程序排空。
   舊版二進位不會理解新標記；必須確認它無法接收新請求或寫入帳本。不要僅
   更換環境變數便宣稱已隔離。首次啟用目前仍需部署執行器與雲端演練。
2. **權限分開**：日常runtime對release-control與確認稽核僅GET；專用controller
   才能CAS控制狀態、create-only稽核及首次綁定標記；observer另有獨立簽署者。
   不接受App帶入manifest、政策、fence或operator簽章；不向App開控制API。
3. **可靠監看與告警**：建議30秒探測、連續兩輪不可觀察即告警；矛盾立即停用。
   這是待驗證運維目標，不是已建排程。監看中斷不再自動停全部顧客，但必須
   另有外部告警，否則不能聲稱持續偵測外部設定漂移。監看與控制寫入同時故障
   時，必須由獨立通道關閉新工作入口，並保留結果讀取／撤回的處置路徑。
4. **失敗回復**：失敗保留標記、意圖及完成紀錄；未確認active拒絕新工作。
   相同未過期命令僅補自己的回執；過期後需新簽署confirm，active再核對即時
   證據。paused恢復必須指定現有狀態，不刪表、不回滾已扣額度。升級前暫停，
   新來源與映像各自完成政策啟用核對後，以新簽署upgrade推進同一控制世代。
5. **競爭界線**：這不是跨控制表與額度表的分散式交易。在停用前已通過最後
   admission檢查的在途請求，可能仍完成一次CAS／執行；不強制撤銷已取得的
   唯一執行權。要求絕對無在途新啟動時，需先關入口並排空，再核對paused。
6. **成本**：日常仍要讀耐久控制與稽核，不宣稱GCS讀取次數下降或零額外成本。
   上線前量測實際GET數、p95延遲及費用，再評估不犧牲停用傳播的方案；本輪
   不以延長allow快取換取效能，也不做無臨床意義的精度重測。
