# 權限分層設計：角色、機構、與後端執行點

> 2026-08-04。觸發：準備釋出給多位測試者試用。
>
> **現況的問題不是「缺功能」，是「稽核軌跡在說謊」**——所有操作的 `actor` 都是 `admin`，
> 而剛完成的 `doctor_verified` 閘門，實際上任何拿到那組密碼的人都能觸發。見 §1。

---

## 1. 為什麼現在就要做

| 現況 | 後果 |
|---|---|
| 所有人共用一組 `admin` | 稽核軌跡的 `actor` 一律是 `admin`——**雜湊鏈能證明紀錄沒被竄改，卻證明不了任何一筆是誰做的** |
| `doctor_verified` 只看「有沒有按完成修邊」 | 護理師、助理、工程師按下去都會產生「醫師已驗證」的 GT |
| 無法停用單一使用者 | 一位測試者離開，只能換掉所有人的密碼 |
| 工程師與臨床使用者權限相同 | 除錯的人看得到病患影像——違反個資最小化 |

第二列是最嚴重的。飛輪的整個前提是 **GT 來自有資格的人的判斷**；
若 `doctor_verified` 無法對應到一位真實的醫師，這批訓練資料在方法學上就站不住。

## 2. 三階段

| 階段 | 內容 | 觸發時機 | 範圍 |
|---|---|---|---|
| **S1 個人帳號 + 角色** | 每人一組帳號、角色決定能做什麼、稽核記真實身分、可停用單一帳號 | **釋出試用前（現在）** | 後端 + App + 主控台 |
| **S2 機構層級** | 院所租戶、資料依機構隔離、院內管理者 | 第二家醫院加入時 | 佇列/統計/匯出/主控台全面加租戶維度 |
| **S3 院內 SSO** | OIDC / LDAP，App 完全不碰密碼 | 正式導入 | 認證層置換 |

### 2.1 為什麼不現在就做 S2

1. 機構維度會滲進**佇列、統計、匯出、主控台、稽核**每一處，而現在只有一個場域——
   等於用猜的去對院方的實際組織（科部？病房？跨院研究團隊？這無法從程式推斷）。
2. 權限錯誤是**靜默地往放行的方向壞**。程式面愈大，破口愈多。
3. 那些多機構程式碼在第二家醫院加入前**一次都不會被執行**。
   沒被執行過的權限控制比沒有更危險——它給人虛假的信心。

### 2.2 但有三件事必須**現在**定好（難以回頭）

| 決策 | 現在怎麼做 | 事後才做的代價 |
|---|---|---|
| **使用者識別碼格式** | `<org>:<user>`，如 `ntuh:dr.chen`。單機構時 org 固定為 `default` | 稽核是 append-only，`actor` 寫成 `admin` 就永遠是那樣，日後無法回溯歸屬 |
| **稽核／佇列紀錄帶 `org` 欄位** | 現在只有一個值也要寫進去 | 事後補欄位＝舊紀錄全是 null，任何「依機構統計」都少了那段歷史 |
| **WD-code 全域唯一** | **已經是**（`WD-` + SecureRandom hex），不需更動 | — |

做到這三件，S2 就是**加功能**而不是**改資料**——
而修改一個裝著真實病歷的資料庫，正是整個專案一路在避免的變更類型。

## 3. 角色定義

角色對應的是**工作內容**，不是職稱。同一個人可以有多重身分（如「醫師兼研究主持人」），
但一次登入只用一個角色——這樣稽核軌跡才回答得出「他當時是以什麼身分做這件事」。

| 角色 | id | 誰 | 核心職責 |
|---|---|---|---|
| 醫師 | `physician` | 主治／住院醫師 | **修邊確認**（GT 的最終責任者）、送訓練標註 |
| 護理師 | `nurse` | 傷口照護護理師 | 拍照量測、存入病歷、輸入滲液 |
| 助理 | `assistant` | 研究助理／實習 | 拍照量測，**不得**存入病歷或確認 |
| 工程師 | `engineer` | 開發與維運 | 範例／模擬圖驗證、系統設定、佇列健康度。**不得接觸臨床資料** |
| 管理者 | `admin` | 專案負責人 | 帳號管理、稽核查詢。**不得**代替醫師確認 |

### 為什麼 `admin` 不能做臨床動作

管理者能新增帳號、能停用他人。若他同時能確認 GT，等於**同一個人可以自己開帳號、
自己扮醫師、自己驗證資料**，稽核軌跡上完全看不出異常。
職責分離（segregation of duties）不是形式，它是稽核之所以有意義的前提。

## 4. 權限矩陣

✓＝允許　✗＝**後端拒絕**（不是只在 UI 隱藏）　△＝限本人建立的資料

| 動作 | physician | nurse | assistant | engineer | admin |
|---|---|---|---|---|---|
| 建立病患／簽同意書 | ✓ | ✓ | ✗ | ✗ | ✗ |
| 撤回訓練同意 | ✓ | ✓ | ✗ | ✗ | ✗ |
| 臨床量測（source=clinical） | ✓ | ✓ | ✓ | ✗ | ✗ |
| 存入個案時間軸 | ✓ | ✓ | ✗ | ✗ | ✗ |
| **修邊確認（doctor_verified）** | **✓** | ✗ | ✗ | ✗ | ✗ |
| 送訓練標註 | ✓ | ✗ | ✗ | ✗ | ✗ |
| 檢視臨床影像／病歷 | ✓ | ✓ | △ | **✗** | ✗ |
| 快速量測（sample/phantom） | ✓ | ✓ | ✓ | ✓ | ✓ |
| 後端設定（位址／帳密） | ✗ | ✗ | ✗ | ✓ | ✓ |
| 飛輪佇列健康度 | ✓ | ✓ | ✗ | ✓ | ✓ |
| 稽核軌跡查詢／驗證 | ✗ | ✗ | ✗ | ✓ | ✓ |
| 帳號管理 | ✗ | ✗ | ✗ | ✗ | ✓ |
| GCP 雲端主控台連結 | ✗ | ✗ | ✗ | ✓ | ✓ |

### 4.1 幾個刻意的選擇

**護理師可以量測與存病歷，但不能確認 GT。**
量測與照護紀錄是護理師的日常職責；而 `doctor_verified` 是**送進訓練集的資料品質背書**，
那是不同性質的責任。護理師按「完成修邊」時，紀錄照樣更新面積與輪廓，
只是 `doctor_verified` 維持 false，該筆不得送訓練標註。
**不是不讓她修邊，是不讓系統以她的名義做醫師的背書。**

**助理不能存入病歷。**
避免未受訓者產生正式紀錄。他可以量測、可以看到結果，但要由護理師或醫師存檔。

**工程師完全看不到臨床資料。**
這是個資最小化，而且非常實際——除錯的人（包含 AI 助理）不需要、也不該需要看到病患影像。
工程師能用快速量測與範例圖重現絕大多數問題；真的需要臨床樣本才能重現時，
應該走「取得授權 → 記錄於稽核 → 限時提權」的程序，而不是預設就給。

**GCP 主控台連結只給工程師／管理者。**
⚠ **GCP 專案權限 ≠ 應用程式權限**。給臨床使用者 GCP Console 存取意味著給他們 IAM 角色，
那會讓他們直接讀儲存桶裡的**原始傷口影像**、看 Secret、刪資源——完全繞過本文件所有閘門。
按鈕本身無害（沒有 IAM 的人只會看到權限不足），但它會誘導人去申請 IAM，
然後某天真的有人給了。臨床角色的正確目的地是**我們自己的 `/console`**：唯讀、去識別、角色可控。

## 5. 後端執行點（權限在哪裡被真的擋下）

> **UI 隱藏不是存取控制。** App 可以被改、APK 可以被反編譯、HTTP 請求可以被偽造。
> 下表每一列都是**伺服器端**的檢查。

| 端點 | 檢查 | 拒絕時 |
|---|---|---|
| `POST /api/v1/annotation` | 角色須為 `physician`；且 `doctor_verified` 由**後端依角色否決**，不採信客戶端送來的值 | 400 + 明確理由，並寫入稽核 |
| `POST /api/v1/classify` | `source=clinical` 須為 `physician`/`nurse`/`assistant` | 403 |
| `POST /api/v1/consent/withdraw`｜`restore` | `physician`/`nurse` | 403 |
| `GET /api/v1/flywheel/stats` | 除 `assistant` 外皆可 | 403 |
| `GET /console` 的資料 | 沿用 stats 權限 | 403 |
| 帳號管理端點 | 僅 `admin` | 403 |

### 5.1 `doctor_verified` 的處理方式

**不是「客戶端送 true 就檢查角色」，而是「後端自己算」：**

```
effective_doctor_verified = client_says_verified AND (role == physician)
```

理由：客戶端送 `false` 時我們相信它（那是保守方向）；送 `true` 時必須由角色背書。
兩邊只要有一邊說不，就是不。這樣即使 App 被改、即使有人直接打 API，
都無法產生一筆「非醫師的醫師驗證」。

### 5.2 稽核記錄

每一筆稽核帶 `actor`（`<org>:<user>` 格式）與 `role`。
**角色要記在稽核裡而不是只查當下的帳號設定**——使用者的角色日後可能變更，
而稽核要回答的是「他當時是以什麼身分做的」。

## 6. UI 呈現原則

| 原則 | 為什麼 |
|---|---|
| **不能做的功能「停用並說明」，而不是隱藏** | 使用者找不到功能會以為壞了、會去問人、會想辦法繞過。看到「此功能需醫師權限」則一次就懂 |
| 例外：**臨床資料對工程師完全隱藏** | 這一項不是能力限制而是資料最小化，隱藏才符合目的 |
| 登入後標題列常駐顯示「姓名（角色）」 | 共用手機時，最常見的錯誤是用上一個人的登入做事。看得到才會發現 |
| 切換角色＝重新登入 | 不做「角色切換」按鈕。一次登入一個身分，稽核才乾淨 |

## 7. 與 IRB／資安審查的對應

| 審查關注 | 本設計如何回應 |
|---|---|
| 誰能存取病患資料 | §4 權限矩陣；工程師與管理者**無**臨床資料存取 |
| 標註品質由誰負責 | `doctor_verified` 僅 `physician` 可產生，且由後端否決（§5.1） |
| 稽核軌跡可否歸屬到人 | `actor` 為 `<org>:<user>`，且記錄當下角色（§5.2）；雜湊鏈保完整性 |
| 人員異動如何處理 | 停用帳號即刻失效；歷史稽核保留原識別碼不改寫 |
| 職責分離 | 管理者不得代替醫師確認（§3） |
| 資料最小化 | 工程師以範例／模擬圖除錯；臨床樣本需另行提權並留痕 |
| 存取權定期複核 | 帳號清單可匯出，供院方定期檢視（S1 提供） |

## 8. S1 實作範圍（下一步）

**後端**
- 帳號改存**儲存層**（`store.py`，本機檔案／GCS 一致）而非環境變數，可新增與停用
- 密碼以 PBKDF2 加鹽雜湊儲存（不可還原）
- JWT 帶 `org`、`role`、`user`
- `annotation` 端點依角色否決 `doctor_verified`；`classify` 依角色限制 `source=clinical`
- 稽核紀錄的 `actor` 改為 `<org>:<user>`，並加 `role`、`org` 欄位
- 帳號管理端點（僅 `admin`）

**App**
- 登入回傳角色 → 依角色停用／隱藏功能
- 標題列顯示「使用者（角色）」
- 工程師／管理者才顯示 GCP 主控台連結；臨床角色顯示飛輪主控台連結

**測試**
- 角色 × 端點的允許／拒絕矩陣
- **重點驗證「後端否決」**：偽造一個 `doctor_verified=true` 的護理師請求，必須被擋

**明確不做**
- 機構隔離（S2）、SSO（S3）、細粒度的資源層級權限（如「只能看自己科部的病患」）
