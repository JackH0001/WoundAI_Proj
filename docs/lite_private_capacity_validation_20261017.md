## 修正

1. GCS CAS 只對明確 HTTP 429 最多額外嘗試三次，等待 1.1／2.2／4.4 秒；保留相同資料及原 generation。遇到競爭更新回傳衝突，不重設 generation；逾時、斷線或其他不明結果仍停止，不當作成功。
2. 空 DELETE 的讀取緩衝下限改為 1 byte，但仍要求零內容；修正 Gunicorn 的 `wsgi.input_terminated` 與 Werkzeug 0 byte 上限互動。非空內容仍拒絕，已簽署空撤回回歸成功。
3. Lite 429／503 回覆提供 `Retry-After`、`retry_after`、`retryable` 及保留待傳資料提示。保留原錯誤與狀態碼；503 仍可能代表保存結果未確認，不能解讀成「完全沒有寫入」。

## 兩平台等待協定（必須完成後才開放大量測試）

使用者要求：同時或大量上傳時，若服務處理不足，要通知前台等待。共同狀態應為「本機待傳 → 等待服務容量 → 傳送中 → 核對保存 → 已保存」，格式／權限錯誤另外顯示。

- 同一修訂只保存一份不可變送件，重試沿用去重鍵及內容；已取得收據的影像、標註不重傳。
- 429／503 必須保留資料並尊重伺服器最早重試時間，額外加入裝置間隨機錯開，避免同時重試；手動按鈕不可越過容量等待。
- 顯示等待原因、下次嘗試時間、待傳筆數與已等待時間；沒有總佇列資訊時，不虛構排位或完成倒數。
- 離開畫面仍保留待傳；系統暫停 App 時不保證背景完成，重新開啟要接續原送件。
- 網路失敗、未登入、同意撤回、無效遮罩與暫時忙碌必須區分；服務繁忙不能提示使用者重拍、重新修邊或改密碼。
- Android 醫療待傳目前能保留 429／5xx，但未完整接收 Retry-After，手動重試仍能略過等待；iOS 醫療以固定退避重試，Lite 修訂保留 pending 但提示仍較籠統。**這些前台接線仍待實作與實機驗收，不能宣稱兩端已完成容量協定。**
- 候選目前 min=0、max=1、concurrency=1，且全域額度共用 GCS CAS 狀態。這是受限驗證配置，不能用 4 客戶端微測試推論大量上傳能力。先量測冷／暖啟動、完整送件 p50／p95、429／503、重送與最終完整率，再決定是否需多實例、分離推論與持久排隊；增加資源另提具體範圍。
