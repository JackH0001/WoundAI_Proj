# WoundAI 雲端管理主控台 — UI 規格與進程

> 搭配 `docs/cloud_platform_plan.md`。這份談的是**人要在雲端做什麼**，不是基礎設施。
>
> 設計前提：飛輪的瓶頸從來不是算力，是**有資格的人的時間**。主控台的每一個畫面都要回答
> 「醫師／資料負責人打開它，能不能在 30 秒內知道下一步該做什麼」。做不到的畫面就不該做。

---

## 0. 使用者與他們真正要的東西

| 角色 | 一天打開一次時想知道 | 最怕的事 |
|---|---|---|
| **臨床資料負責人** | 收案進度到哪、有沒有卡住的個案 | 收了一堆才發現不能用 |
| **標註審核醫師** | 有幾筆等我看、哪幾筆有疑慮 | 審過的東西進了訓練集卻沒人告訴我後來怎麼了 |
| **模型負責人** | 新版有沒有比舊版好、能不能上線 | 模型悄悄退步而沒人發現 |
| **法遵／IRB 窗口** | 撤回請求處理了沒、稽核軌跡查得到嗎 | 稽核時拿不出證據 |

**刻意不服務的角色**：一般醫護。他們的介面是手機 App，不該來雲端後台。
多開一個入口就多一條繞過同意閘門的路。

---

## 1. 資訊架構

```
主控台
├─ 總覽              ← 預設頁。四張卡 + 待審 + 晉升閘門（見附圖）
├─ 標註審核          ← 醫師的主要工作區
│   ├─ 待審佇列（只列 clinical，其餘另分頁）
│   └─ 單筆審核：影像＋遮罩疊圖 → 接受／退回／標記爭議
├─ 資料集與訓練
│   ├─ 資料集快照（不可變，含資料卡與樣本指紋）
│   └─ 訓練任務（GPU spot，狀態與日誌）
├─ 模型治理
│   ├─ 版本清單（線上／候選／已退役）
│   ├─ 晉升閘門（四項門檻，全過才可上線）
│   └─ 回滾
├─ 同意與稽核
│   ├─ 撤回請求（處理狀態、影響到哪幾筆）
│   └─ 稽核軌跡查詢與匯出
└─ 機構與帳號
```

## 2. 各畫面的設計決定（與理由）

### 2.1 總覽

四張卡：**臨床收案進度**、**佇列可訓練**、**待審標註**、**線上模型**。

- **收案進度只算 `by_source.clinical`。** 範例與模擬圖走同一條管線收進來，混進分子會讓
  「我們已經收了 20 例」變成假的——而那個數字要寫進 IRB 報告與模型資料卡。
- **「佇列可訓練」旁邊必須並列孤兒 GT 與影像遺失的筆數。** 只顯示可訓練數，
  資料鏈壞掉時畫面依然一片綠（2026-07-28 的稽核就是這樣才發現 8/8 筆不可用）。
- 待審逾期要變色。審核延遲是飛輪停轉最常見的原因，而它不會自己發出聲音。

### 2.2 標註審核

單筆畫面：原影像 + AI 遮罩 + 醫師修邊後遮罩**三層疊圖**，可切換顯示。

| 元素 | 為什麼要有 |
|---|---|
| 修邊 IoU | 一眼看出醫師改了多少。接近 1.0 表示 AI 幾乎對了；很低則要看是模型錯還是醫師畫錯 |
| `image_reused` 警示 | 同一批位元組先前上傳過 → 幾乎必然是範例圖被當成臨床樣本。**實測發生過** |
| 同意狀態 | 審核當下重讀，不用列表載入時的快照。病患隨時可能撤回 |
| 「退回」要填理由 | 退回而不說為什麼，等於把問題丟回給不知道發生什麼事的人 |
| 相鄰回診的同案縮圖 | 判斷這次的輪廓合不合理，最有效的參照是同一個傷口的上一次 |

**多讀者一致性（ICC）列為第二階段。** 單讀者的 GT 有系統性偏誤，但在 n=20 階段
強迫雙讀者會直接讓收案停擺。先把單讀者跑順，累積到足以做 ICC 再加。

### 2.3 資料集與訓練

**資料集快照不可變。** 訓練任務綁定的是快照 ID，不是「當下的佇列」。
沒有這一條，「這個模型是用哪些資料訓練的」永遠答不出來——而那正是稽核第一個問的問題。

每個快照自動產生資料卡：樣本數（按 source 拆）、撤回排除數、被取代數、日期範圍、
影像尺寸分布、標註者。這在 `export_flywheel_dataset.py` 已有雛形，搬上雲即可。

### 2.4 模型治理 — 晉升閘門

**四項門檻全過才可上線，且不提供覆寫按鈕。**

| 門檻 | 為什麼 |
|---|---|
| golden Dice 不得低於現行線上版 | 防止悄悄退步。這是最基本的一條 |
| 面積誤差維持在既有實測區間內 | 面積是臨床實際使用的數字，比 Dice 更直接 |
| 訓練集不得含已撤回樣本 | 撤回承諾要在模型層面成立，不只在佇列層面 |
| 臨床樣本比例達標 | 防止用範例／模擬圖灌出好看的指標 |

**為什麼不給覆寫**：閘門一旦有例外，實務上就會變成常態。真的需要放行時，
正確做法是改門檻並留下紀錄，而不是按一個「我知道風險」的按鈕。

### 2.5 同意與稽核

- 撤回請求要顯示**影響範圍**：這個 code／影像牽連到佇列裡哪幾筆、哪些資料集快照用過它。
  只說「已撤回」而不說影響了什麼，等於沒有給法遵可用的答案。
- 稽核軌跡**唯讀、可匯出、不可刪**。上雲後要有技術保證（雜湊鏈 + WORM），
  不能只靠「大家都不刪」的約定。

## 3. 進程規劃

| 階段 | 內容 | 前置 | 估時 |
|---|---|---|---|
| **C0** 唯讀總覽 | 四張卡 + 佇列健康度。直接讀現有 `/flywheel/stats` | 無 | 3–5 天 |
| **C1** 標註審核 | 待審清單、疊圖檢視、接受／退回／爭議 | C0、佇列進 Postgres | 2–3 週 |
| **C2** 資料集與訓練 | 不可變快照、資料卡、訓練任務觸發與狀態 | C1 | 2–3 週 |
| **C3** 模型治理 | 版本清單、晉升閘門、回滾 | C2、golden 測試自動化 | 2 週 |
| **C4** 同意與稽核 | 撤回影響範圍、稽核查詢與匯出、雜湊鏈 | C1 | 2 週 |
| **C5** 多讀者 ICC | 雙讀者指派、一致性統計 | C1 + 足夠樣本量 | 3 週 |

**C0 可以現在就做**，而且值得——它只是把手機設定頁已經在顯示的統計換成網頁，
但讓不拿手機的人（資料負責人、法遵）也看得到收案進度。

**C1 之後才是真正的分水嶺**：在那之前，標註審核靠人工看 jsonl；在那之後，
飛輪才有機會在多院規模下運轉。

## 4. 明確不做

- **不做給一般醫護的雲端入口。** 他們的介面是手機 App。多一個入口＝多一條繞過同意閘門的路。
- **不做「一鍵重新訓練」。** 訓練要綁定不可變快照並留下觸發者，不是按鈕按下去就跑。
- **不在主控台顯示任何 PII。** 雲端本來就沒有——這一條寫在這裡是為了防止日後有人
  「為了方便對照」而把姓名同步上來。那會一次拆掉整個架構最重要的合規槓桿。
- **不做即時推播通知。** 待審逾期在總覽變色就夠。推播會訓練出「已讀不回」的習慣，
  之後真正緊急的事也叫不動人。
