# WoundAI 雲端後端平台：資源評估與導入規劃

> 2026-08-03。所有效能數字是**在本專案的實際模型上實測**，不是估算；成本與法規部分標明來源。
> 結論先講：**這個工作負載不需要 GPU，而且現在還不該上雲**。理由見 §1 與 §6。

---

## 0. 一句話結論

| 問題 | 答案 |
|---|---|
| 要不要 GPU？ | **不要**。實測全流程 CPU 上 87 ms（一般）／796 ms（難例集成），2 vCPU 撐得住每日 5000 次量測 |
| 要多少錢？ | 小規模多院約 **US$120–180/月**；全國規模約 **US$1000–1500/月**。主要成本不是推論，是資料庫與可觀測性 |
| 用哪家雲？ | **AWS 台北（ap-east-2）或 GCP 彰化（asia-east1）**。法規要求醫療雲端儲存地點以境內為原則；Azure 台灣區尚未上線 |
| 什麼時候上雲？ | **n=20 收案完成、確認模型有提升之後**。現在上雲只是在還沒有東西要規模化時增加變數 |

## 1. 實測負載（2026-08-03，2 vCPU、ONNX Runtime 1.23.2 CPU EP）

### 1.1 推論

| 模型 | 輸入 | 中位數 | P90 | 檔案 |
|---|---|---|---|---|
| `student_fp16.onnx` | 1×3×256×256 | **55.0 ms** | 58.9 ms | 13.3 MB |
| `a_unet.onnx` | 1×256×256×3 | 203.7 ms | 218.4 ms | 32.5 MB |
| `unetpp.onnx` | 1×256×256×3 | 504.6 ms | 540.2 ms | 36.6 MB |

### 1.2 前後處理（2048×1536 上傳影像）

| 步驟 | 耗時 |
|---|---|
| JPEG 解碼 | 5.7 ms |
| resize → 256 | 0.2 ms |
| 輪廓 `findContours` | 11.4 ms |
| ArUco 偵測（全尺寸） | 14.6 ms |
| **小計** | **≈ 32 ms** |

### 1.3 單次請求總成本

| 路由 | 組成 | 總延遲（2 vCPU） |
|---|---|---|
| 一般（student） | 32 + 55 | **≈ 87 ms** |
| 難例集成（`cloud_escalated(AU)`） | 32 + 55 + 204 + 505 | **≈ 796 ms** |
| 模擬圖（`phantom_color`，純 HSV） | 32 + ~5 | ≈ 37 ms |

**關鍵觀察**：`unetpp` 一個模型就佔掉集成路由的 63%。若日後要壓延遲，先動它（量化成 INT8 或換更小的第二意見模型），而不是加硬體。

## 2. 容量推算

假設難例升級率 20%（保守；實際由分歧度門檻決定），平均服務時間
`0.8 × 0.087 + 0.2 × 0.796 = 0.23 秒`（牆鐘）≈ **0.46 CPU-秒／次**。

門診的量測不是均勻分布——晨間查房會集中，取「**60% 的量落在 3 小時內**」。

| 情境 | 每日量測 | 尖峰 req/s | 平均佔用核心數 | 建議規格 |
|---|---|---|---|---|
| 試點（1 院，n=20） | ~10 | 0.002 | 0.001 | 一台筆電就夠 |
| 小規模（3–10 院） | 60–200 | 0.011–0.037 | 0.005–0.017 | 2 vCPU / 4 GB |
| 中規模（20–50 院） | 600–1500 | 0.11–0.28 | 0.05–0.13 | 2× 2 vCPU（為了 HA，不是為了效能） |
| 全國規模（100+ 院） | 5000 | 0.93 | **0.43** | 2–3× 4 vCPU |

**即使全國規模，平均也只吃掉不到半顆核心。** 之所以還要開 2–3 台，是為了

1. **可用性**（單台重啟就全院停擺不可接受）、
2. **尾端延遲**（集成路由 796 ms 佔著執行緒時，後面的請求要等）、
3. **滾動更新**（換模型版本不中斷服務）。

> ### 什麼時候才真的需要 GPU？
>
> 要讓 GPU 划算，得同時滿足「每一次都跑集成」且「持續超過約 20 req/s」——那是**每天 170 萬次量測**。
> 全台灣的傷口照護量體差好幾個數量級。
> 現在配 GPU（L4/A10G 約 US$0.5–1.0/hr ≈ **US$360–720/月**）是把預算燒在閒置的加速器上。
> GPU 真正該出現的地方是**離線再訓練**，而那是間歇性的，用 spot 幾小時即可（見 §5.3）。

## 3. 儲存與流量

實際樣本量測（本專案 `flywheel/images/`）：62 KB – 421 KB，取平均 **300 KB**。

| 情境 | 影像/日 | 每月新增 | 每年累積 | 物件儲存月費* |
|---|---|---|---|---|
| 小規模 | 200 | 1.8 GB | 22 GB | < US$1 |
| 中規模 | 1500 | 13.5 GB | 162 GB | ~US$4 |
| 全國規模 | 5000 | 45 GB | 540 GB | ~US$13 |

\* 以標準物件儲存約 US$0.023/GB/月計。

**儲存不是成本問題。** 加上遮罩 PNG 與 metadata 也就翻倍。真正要注意的是**保存期限與刪除**：
App 端已做「結案逾 90 天刪影像、保留數值」，雲端要有對應的生命週期規則，否則 IRB 承諾的
「逾期即下架／銷毀」在雲端側落空。

流量：上傳 300 KB／次，全國規模每日 1.5 GB。多數雲**入站免費**；出站只有 JSON 回應，可忽略。

## 4. 法規約束（這一節決定雲平台選擇，不是成本）

| 要求 | 出處 | 對本案的意義 |
|---|---|---|
| 病歷、醫療資料屬**特種個資**，原則禁止蒐集處理利用 | 個資法 §6 | 傷口影像縱使去識別，仍應以特種個資規格對待 |
| 醫療機構採用雲端服務，**儲存地點以我國境內為原則**；位於境外者須附境外個資法文件交中央主管機關審核 | 衛福部醫療機構委外規範 | **region 必須選台灣**。這一條直接淘汰沒有台灣區的雲 |
| 委外須簽書面契約，涵蓋受託範圍、權義等 10 項；使用非自行開發系統須說明來源與授權 | 同上 | 要備妥 DPA、SBOM、開源授權清單（`smp` 的 MIT 授權須列入） |
| 跨境傳輸採「原則允許、例外限制」，但主管機關可隨時限縮 | 個資法 §21 | 即使技術上可用境外區，也不該把架構綁死在境外 |

### 本專案的合規槓桿：PII 從一開始就不上雲

架構上**姓名、病歷號只存在手機的 Keystore 加密區**，離開裝置的只有 `WD-` 去識別代碼。
這讓雲端側的個資範圍大幅縮小，但**不等於零**——傷口影像在極端情況仍可能帶有可識別特徵
（刺青、疤痕、背景中的識別證）。規劃上一律以特種個資規格處理，不因「已去識別」而放寬。

### 雲平台可用性（2026-08）

| 雲 | 台灣區 | 狀態 |
|---|---|---|
| **AWS** | Asia Pacific (Taipei) `ap-east-2` | 已 GA，3 個可用區 |
| **GCP** | `asia-east1`（彰化） | 已營運多年 |
| **Azure** | Taiwan North | **尚未上線**（2020 年宣布，仍為 coming soon） |
| 本土（中華電信 hicloud 等） | — | 合規最單純，但託管服務生態較薄，維運人力成本會轉嫁回團隊 |

**建議：AWS 台北或 GCP 彰化二選一。** 判準不是價格（兩者差距在本案規模下每月幾十美金，
不足以構成決策依據），而是：

- 已經在用哪家的其他服務（減少一套帳號、IAM、計費、稽核）
- 團隊熟哪一套 IAM 與稽核工具（安全設定錯誤的風險遠大於價差）
- 醫院資安審查偏好哪一家（實務上這一條往往最有份量）

## 5. 目標架構

```
┌─ 手機（受控、加密）─────────────┐
│ 姓名・病歷號 → Keystore 加密    │   PII 永不離開
│ WD-code ─────────────────────┐ │
└──────────────────────────────│─┘
                               ▼  HTTPS + JWT（未來：院內 SSO 短效 token）
                    ┌──────────────────────┐
                    │  WAF / 應用負載平衡   │  IP 白名單：只放行合作院所出口
                    └──────────┬───────────┘
                               ▼
                 ┌─────────────────────────┐
                 │  推論服務（容器 × 2–3）  │  student / 難例集成 / 色彩分割
                 │  ONNX Runtime CPU        │  健康檢查、滾動更新
                 └───┬──────────┬──────────┘
                     │          │
        ┌────────────▼──┐   ┌───▼──────────────┐   ┌──────────────────┐
        │ 物件儲存        │   │ Postgres          │   │ 模型登錄          │
        │ 影像／遮罩      │   │ 標註佇列・撤回墓碑 │   │ 版本・資料指紋    │
        │ SSE-KMS 加密    │   │ 稽核軌跡           │   │ golden 指標       │
        │ 生命週期規則    │   │ （append-only）    │   └──────────────────┘
        └────────────────┘   └───────────────────┘
                     │
                     ▼  （間歇、離線）
        ┌──────────────────────────────┐
        │ 再訓練：GPU spot 數小時／月    │
        │ → 評測門檻 → 通過才進模型登錄  │
        └──────────────────────────────┘
```

### 5.1 從現況要改的三件事

| 現況 | 問題 | 目標 |
|---|---|---|
| `retrain_queue.jsonl` 檔案 append | 單機可行；**多實例並發寫會交錯損壞** | Postgres 表，維持 append-only 語意（不 UPDATE，撤回＝新增墓碑列） |
| `flywheel/images/<sha1>.jpg` 本地檔 | 容器重啟即消失；多實例看不到彼此的影像 | 物件儲存，鍵值維持內容 sha1（去重與 `image_reused` 偵測邏輯不變） |
| 明文帳密（已改為本機加密儲存） | 仍是長效密碼 | 後端改發短效 token；院內 SSO 為終局 |

**做法建議：先抽介面，不要先搬家。** 在現有 `api_flywheel.py` 把「佇列讀寫」與「影像讀寫」
各抽成一個介面，本機實作維持檔案版。這樣本機開發與 CI 完全不變，而上雲時只是換一個實作。
反過來先搬到雲上再抽介面，會讓本機從此跑不起來——那是團隊生產力的災難。

### 5.2 稽核軌跡不可竄改

`audit.jsonl` 目前靠「只 append、不刪」的約定。上雲後要有技術保證：

- 物件儲存的 **Object Lock / WORM**（保留期內任何人都刪不掉，含管理員），或
- 稽核表加 **雜湊鏈**（每列存前一列的雜湊），定期把鏈頭雜湊寫進 WORM 儲存

第二種較輕、且本機也能跑，建議先做雜湊鏈。

### 5.3 再訓練：唯一需要 GPU 的地方

- 資料量級：n=20 起步，目標數百到數千張
- 一次微調（UNet 系、256²、數千張）在單張 L4/A10G 上約 **1–3 小時**
- 頻率：每累積一批新標註跑一次，實務上**每月 1–4 次**
- 成本：spot 約 US$0.2–0.4/hr → **每月 US$2–15**
- **不需要常駐 GPU 節點**。用得到時才開，跑完就關

## 6. 分階段導入與成本

### 階段 A｜現在～n=20 收案完成：**不上雲**

在醫院內一台電腦跑現有的 `app.py`，手機經院內 Wi-Fi 連。
成本 **US$0**。

**為什麼不現在上雲**：n=20 的目的是驗證「飛輪能不能讓模型變好」。這個問題的答案與部署位置無關，
而上雲會引入網路、憑證、region、IAM 等一整排新變數——在還沒有東西需要規模化的時候。
真正該在這個階段做的雲端準備只有兩件：**抽出儲存／佇列介面**（§5.1）與**容器化**（`Dockerfile` 已有）。

### 階段 B｜小規模多院（3–10 院）

| 項目 | 規格 | 月費（US$） |
|---|---|---|
| 推論服務 | 2 vCPU / 4 GB × 1 | 45–55 |
| 託管 Postgres | 最小規格 + 自動備份 | 30–60 |
| 物件儲存 | 50 GB + 請求 | 2 |
| 負載平衡 + TLS | 1 個 ALB | 20 |
| 日誌／監控 | 基本量 | 10 |
| **合計** | | **≈ 120–180** |

### 階段 C｜中規模（20–50 院）

| 項目 | 規格 | 月費（US$） |
|---|---|---|
| 推論服務 | 2 vCPU × 2（HA + 滾動更新） | 100 |
| 託管 Postgres | 含唯讀複本 | 120–150 |
| 物件儲存 | 200 GB | 5 |
| 負載平衡 + WAF | | 50 |
| 可觀測性 | 指標／日誌／追蹤 | 50 |
| 再訓練 GPU | spot，每月數小時 | 5–15 |
| **合計** | | **≈ 350–500** |

### 階段 D｜全國規模（100+ 院）

| 項目 | 月費（US$） |
|---|---|
| 推論服務 4 vCPU × 3 | 300 |
| Postgres（HA + 複本） | 400 |
| 物件儲存 600 GB + 生命週期 | 15 |
| LB / WAF / DDoS | 150 |
| 可觀測性 | 150 |
| 備援與跨區備份 | 100 |
| 再訓練 GPU | 15 |
| **合計** | **≈ 1100–1500** |

**成本結構的重點**：從階段 C 起，**資料庫與可觀測性加起來超過運算**。
想省錢要從那裡下手（例如日誌採樣、冷資料下沉），而不是繼續砍已經很便宜的推論節點。

### 不在上表內、但一定會發生的成本

- **醫院資安審查**：每一家都要做一次，人力為主，可能要求滲透測試報告
- **法規文件**：DPA、SBOM、開源授權清單、ISO 27001 或等同的控制項對照
- **值班與事故回應**：臨床系統壞掉不能等上班，這是人的成本
- **模型再訓練的人工標註審核**：飛輪的瓶頸從來不是算力，是有資格的人的時間

## 7. 風險與不做的事

| 風險 | 緩解 |
|---|---|
| 過早規模化，把還在變的架構凍在雲上 | 階段 A 不上雲；先抽介面再搬家 |
| 影像雖去識別仍可能可再識別 | 一律以特種個資規格處理；不因去識別而放寬控制 |
| 主管機關限縮跨境傳輸 | 從第一天就選台灣 region，不把架構綁死在境外 |
| 稽核軌跡遭竄改（含內部人） | 雜湊鏈 + WORM，管理員也刪不掉 |
| 模型退步而沒人發現 | 模型晉升必須通過 golden 指標門檻，不通過不上線 |

**明確不做**

- **不上 Kubernetes**（階段 D 之前）。兩三個容器用託管容器服務就夠，K8s 的維運成本會吃掉整個團隊。
- **不做多雲**。合規與稽核要對兩套，收益為零。
- **不建常駐 GPU 節點**。理由見 §2。
- **不把 PII 搬上雲**。這是本架構最大的合規槓桿，一旦讓步就再也拿不回來。

## 8. 里程碑

| 里程碑 | 內容 | 前置 |
|---|---|---|
| **M0** 雲端就緒（不部署） | 抽出儲存／佇列介面；容器化驗證；SBOM 與授權清單 | 無，可與收案並行 |
| **M1** n=20 收案完成 | 真實臨床照跑通飛輪；模型是否提升有結論 | 真機連線（已完成）、IRB |
| **M2** 單院雲端試營運 | 階段 B 架構；台灣 region；WORM 稽核 | M0 + M1 |
| **M3** 管理主控台 | §9 的畫面；標註審核與模型治理 | M2 |
| **M4** 多院擴張 | 階段 C；HA、可觀測性、值班 | M3 + 資安審查 |

**M1 是唯一的關鍵路徑。** M0 可以並行，但不要讓 M0 變成拖延 M1 的藉口——
沒有臨床資料，雲平台再漂亮也只是空轉的基礎設施。
