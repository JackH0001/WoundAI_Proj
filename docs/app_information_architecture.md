# App 資訊架構與流程優化提案

> 觸發：Sprint N1 個案管理落地後，它被塞在「AI 量測驗證(模擬)」→ 第三層，
> 而真正的臨床工作流也在同一顆按鈕後面。主畫面該重排了。

## 1. 現況診斷

主畫面（`MainActivity.kt:88-99`）是**依程式模組列功能**，不是依醫護要做的事：

| 按鈕 | 去向 | 問題 |
|---|---|---|
| 開始量測 | `CaptureScreen` | **不綁個案**、結果不進時間軸 → 專門生產孤兒紀錄；與下面的量測路徑並存 |
| 查看歷史紀錄 | `WoundTimelineScreen` | 全域撈，所有病患混一條趨勢線（臨床上無意義） |
| 設定 | `SettingsScreen` | — |
| 醫師標註系統 | `DoctorAuthActivity` | **死路**：密碼已清成 `REMOVED_USE_BACKEND_AUTH`（`:167-174`），誰都登不進去 |
| AI 量測驗證(模擬) | `MeasureValidationEntry` | **真正可用的完整流程在這裡**，名字卻寫「模擬」；個案管理再往下一層 |

**核心症狀**：兩條並行的量測路徑（一條綁個案、一條不綁）、一個誤導性命名、一個死路入口、
一個臨床上沒意義的全域趨勢圖。

### 「歷史紀錄」是兩種東西被混在一起

| 用途 | 正確歸屬 | 理由 |
|---|---|---|
| **趨勢分析**（面積折線、癒合率） | **個案內** | 一位病患可能同時有薦骨壓瘡與右足潰瘍，曲線完全不同；混畫沒有臨床意義 |
| **最近活動**（今天量了誰、久未追蹤者） | **主畫面** | 這是導覽與提醒，不是分析。應為清單＋跳轉，**不畫趨勢圖** |

所以不是把歷史紀錄「搬進」個案管理，是**把它拆成兩個不同的東西**。

## 2. 目標架構

```
主畫面（工作台）
├─ 【個案】                    ← 主要工作流，第一順位
│   ├─ 最近就診（近 7 天有量測的個案，一鍵接續）
│   ├─ 病患清單／＋新增病患
│   └─ 病患 → 知情同意 → 傷口個案 → ┬─ 量測（拍照→classify→修邊→存檔→送標註）
│                                    └─ 時間軸（**只畫這個傷口**）
│
├─ 【快速量測】                 ← 不綁個案：範例圖／模擬圖驗證、開發檢錯
│   └─ 來源＝範例／模擬圖（臨床選項在此隱藏，避免無個案的臨床紀錄）
│
└─ 【設定與工具】
    ├─ 後端連線／模型狀態
    ├─ 飛輪佇列健康度（by_source.clinical 收案進度）
    └─ 資料匯出
```

### 主要流程（臨床）

```
開 App → 個案 → [最近就診] 直接點該個案      ← 回診：兩步到量測
                 或 病患清單 → 選/新增病患
                        → 同意書（首次必簽，之後略過）
                        → 選/新增傷口個案（配發穩定 WD-code）
                → 拍照 → classify → 修邊 → 存入時間軸
                       → （有②訓練同意才顯示）送訓練標註
```

## 3. 變更清單

### P0 — 移除誤導與死路

| # | 變更 | 理由 |
|---|---|---|
| 1 | 「AI 量測驗證(模擬)」→ 拆成「個案」與「快速量測」兩個入口 | 目前的完整臨床流程被一個寫著「模擬」的按鈕遮住 |
| 2 | 移除／隱藏「醫師標註系統」 | 密碼已被清空成無法登入的字串，留著只會讓人以為壞了。要恢復應改走後端認證，非本輪 |
| 3 | 「開始量測」(`CaptureScreen`) 併入個案流程或移除 | 兩條並存必然產生 `caseId=null` 的孤兒紀錄，這正是 N1 要根治的 |

### P1 — 個案優先

| # | 變更 | 理由 |
|---|---|---|
| 4 | 主畫面第一項＝「個案」 | 它是唯一的臨床工作流入口 |
| 5 | 全域趨勢圖降級為「最近活動」清單（點了跳個案） | 趨勢已在個案內；全域混畫誤導 |
| 6 | 從個案進入量測時，來源自動＝`clinical` 並**鎖定**（不再問） | 已選個案就不可能是範例；少一次必選、也少一次選錯 |
| 7 | 「快速量測」隱藏「臨床」選項 | 沒有個案的臨床樣本＝孤兒，從入口就擋掉比事後提示好 |

### P2 — 流程順手

| # | 變更 | 理由 |
|---|---|---|
| 8 | 個案卡顯示「上次面積 / 變化% / 距上次天數」 | 醫護真正要的決策資訊；目前只顯示部位＋WD-code |
| 9 | 臨床模式預設「拍照」而非「相簿」 | 現場拍攝是常態；相簿只在補件時用（且事後匯入有壓縮風險） |
| 10 | 「存入時間軸」不應被滲液輸入卡住（可討論） | 滲液是 PUSH 子分；「留一筆照護紀錄」不該被評分欄位擋下。反面理由：避免半殘紀錄。**留給臨床端決定** |
| 11 | 同意狀態列常駐於個案內 | 醫師隨時看得到「訓練同意✓/✗」，不必進管理頁 |

### P3 — 之後（非本輪）

- 底部導覽列（個案／量測／設定）取代按鈕清單 —— 三個以上的主入口用 bottom nav 是標準做法
- 個案結案／重開流程
- 多讀者標註（ICC）所需的 UI

## 4. 最小落地路徑

若要一次到位工作量偏大，建議這個順序（每步都可獨立驗證）：

1. **主畫面重排**（P0-1、P0-2、P1-4）：改 `MainActivity` 的按鈕與 `when` 分支，
   新增 `"cases"` 分支直接進 `CaseSelectScreen`。**不動任何既有畫面內部**。
2. **量測入口分流**（P1-6、P1-7）：`MeasureValidationEntry` 加一個參數區分「臨床／快速」，
   臨床模式鎖 `source=clinical`、快速模式隱藏臨床選項。
3. **時間軸接個案**（P1-5）：個案卡加「時間軸」按鈕 → `WoundTimelineScreen(caseId=…)`；
   主畫面的「查看歷史紀錄」改成最近活動清單。
4. **個案卡資訊**（P2-8）：`CaseRepository.caseSummary(caseId)`，回上次面積、相對首次的變化%、天數。

## 5. 不要做的事

- **不要在主畫面直接放「拍照」**：沒有個案綁定的照片就是孤兒紀錄，這是 N1 剛修完的問題。
- **不要保留全域趨勢圖**：它把不同病患、不同部位的傷口畫成一條線，是會誤導臨床判斷的圖表。
  要保留「總覽」的話，正確做法是**每個個案一條線**的多線圖，或乾脆只給清單。
- **不要為了 demo 方便而讓臨床流程可以跳過同意書**：閘門一旦有例外，實務上就會變成常態。

## 6. 實作結果（2026-07-28）

四步全部落地。除了原規劃，程式碼審查另外抓出並修掉這些（**都是靜態看程式碼看不出來、要跑起來才會爆的**）：

| 問題 | 為什麼危險 |
|---|---|
| **撤回「訓練」同意會連「照護」一起撤掉** | `consents.withdraw()` 標的是整列，而 `countActiveCare` 濾 `withdrawnAt IS NULL` → 病患從此不能量測，流程直接鎖死。雙層同意的語意是「②可撤回、①不受影響」。修法：撤回後補簽一筆保留照護、關閉訓練的紀錄（舊紀錄留痕） |
| **`viewModelScope.cancel()` 會殺掉存檔** | 醫師按完「存入時間軸」立刻返回 → Room 寫入被取消、紀錄靜默消失，畫面已離開連錯誤都看不到 |
| **`seg.release()` 關掉 process 級 OrtEnvironment** | 反覆進出量測頁等於把整個 App 的 ORT 環境關掉 |
| **同意閘門只擋「載入影像」** | 載入後才撤回同意的話，「存入時間軸」照樣按得下去。閘門要放在每一個會產生資料的動作上 |
| **`case` 未 saveable** | 轉螢幕會把「切換後的個案」悄悄換回進來時那個，接著存檔就寫進**錯的時間軸** |
| **最近就診繞過照護同意** | 個案清單有擋，但這是第二個入口。只擋一個入口＝沒擋 |
| **`recentCases` 的結案過濾在 SQL LIMIT 之後** | 最近 10 個剛好都結案時，清單整頁空白而其實還有開立中的個案 |
| **返回鍵直接結束 App** | 沒有 `BackHandler`；修邊頁按返回會丟掉醫師手畫的遮罩且無確認 |

### 已知未解（下一輪）

- `MeasureViewModel` 是手動 `new` 的，`onCleared()` 永不呼叫。正解是改用 `viewModel()`，需先補 `lifecycle-viewmodel-compose` 相依。
- 快速量測仍可把真實臨床照標成「範例」送出，繞過同意鏈。程式擋不住（無法判斷照片是不是真人），屬**流程與訓練**問題，須寫進 SOP。
- `recentRows()` 是 N+1（10 個個案 ≈ 50 次查詢＋10 次 Keystore）。都在 IO 上不會 ANR，清單長了再改聚合 SQL。
- `CaptureScreen` / `HistoryScreen` / `DoctorAuthActivity` 已無入口但程式碼仍在，屬死碼。
