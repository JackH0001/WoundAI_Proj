# WoundAILite：跨程序刪帳與晚到辨識結果驗收

基準 `64cc0bf`，本輪只新增合成驗收工具與證據，不改產品後端、iOS 或資料政策。
既有單元測試已涵蓋同一程序中的關閉／寫入競爭；本輪把刪帳改由另一個實際
Gunicorn 程序經已簽署 HTTP 送達，另在私人處置程序封存同一結果欄位，確認 CAS
不讓晚到的工作重新寫回資料。不是正式雲端驗收，也不是完整刪帳完成聲明。

## 實際執行

- 固定 native 映像仍是 `a175a1549fce89c9910a890eaa4b8c3f33c056fb`，digest
  `sha256:53eed5b05162d751c3311f77f863077eb57e5742ba65a98ee439c79c28a14195`。
  72 個封裝程式／設定與本輪基準逐檔相同；模型及全部 75 個封裝檔案在映像內核對。
- Linux amd64、UID 1000、唯讀映像、無外部網路、無主機掛載、兩個 Gunicorn 程序；
  共享 SQLite，實際 ONNX。Apple、OAuth、KMS、GCS 傳輸及時鐘使用合成替身。
- 每個情境皆獨立建立合成帳號，先成功完成一筆，第二筆在指定位置等待；程序 B
  送出「刪帳並撤回可對應研究」要求，私人處置元件再封存兩個結果欄位。
- 延遲只發生在測試掛鉤；原帳號判定、模型、使用量、結果 CAS、稽核與 HTTP 路由
  都來自固定映像，沒有將成功回應或封存結果預先造假。

| 情境 | 晚到請求 | 結果與額度 |
| --- | --- | --- |
| 模型執行中，另一程序先受理刪帳 | 409 `lite_operation_conflict`，保留本機 | 不保存晚到遮罩；成功次數維持 1 |
| 已完成模型及帳號檢查，在 CAS 寫入前先封存結果 | 410 `lite_operation_expired`，不得自動重跑 | 舊 revision 無法覆寫封存標記；成功次數維持 1 |
| 刪帳後的新工作、已完成結果查詢 | 401 | 不再提供結果或啟動新模型 |
| 重啟一個服務後，重送原刪帳及工作 | 刪帳 202、工作／結果查詢 401 | 原刪帳及封存狀態不變，無額外模型與成功扣額度 |

兩個情境各執行模型 2 次（原成功 1 次＋刪帳時已在執行的 1 次），各只有 1 次成功
扣額度。已執行但未結算的工作仍保留在帳本：`attempts=2、used=1、pending=1`。
不把已執行的工作假稱從未開始，也不任意重設帳本或新增成功收據。已完成那筆的
原收據及帳本完全保留，舊稽核列不被改寫；原合成 JPEG 雜湊與研究 privacy 狀態不變。

本輪直接呼叫私人 **current-result lane**，沒有呼叫整個刪帳協調器，也沒有撤銷
Apple token、銷毀 KMS、清研究影像／備份。故聚合進度仍顯示處置尚未開始或待完成，
`account_deleted=false`；lane 的封存收據不能冒充整體刪除完成。本輪只驗證私人
處置元件與 HTTP／模型競爭的邊界，後續仍須完整工作執行器及真實 provider 驗收。

## 證據與限制

`tools/probe_lite_native_closure_race.py` 可在已核對的 native 容器中執行；需要專案
合成 fixture 及既有授權模型，不從網路下載。兩個情境共 4 次模型執行，不是 4 個
獨立準確度樣本，也不是負載測試。此次只有單裝置身分的跨程序請求，不宣稱跨裝置
App Attest 同時序列已驗證。

`tools/verify_lite_closure_race_evidence.py runtime-probe.json` 在 Windows/Mac 可離線
核對保留的兩個情境、HTTP 回應、封存／收據綁定及額度；不重跑產品、不呼叫雲端。
原始日誌、來源／映像雜湊、QA manifest、VM 已停止證據均留在本機覆核包。

第一次工具誤以為已受理但後來關帳的請求應回 401；既有 HTTP 契約實際把
`AccountClosing` 映射為 409。工具改為精確核對 inference=409、CAS=410 後通過，
產品未改；第一次失敗、原 QA 包與修正說明皆保留，沒有把失敗算成通過。

本輪未合併、部署、改 IAM、更新 Apple 或操作原研究資料。正式外測仍須候選服務、
真實 Apple Sandbox、有效權限、完整清冊／歷史版本／金鑰退休及資料處置驗收。
