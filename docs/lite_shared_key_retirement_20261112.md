# 共用金鑰退休：盤點、存活帳號與復原副本的整合關卡

本輪接續 `14f5d60`。先前的低層操作元件只保證固定 KMS 版本、操作唯一性及不明結果續接，沒有驗證資料是否真的能在停用舊金鑰後恢復。`SharedKeyRetirement` 現在把**指定來源盤點、實際 DEK 解密比對、原始稽核、獨立範圍簽署與原操作元件**接起來。

它仍是私有、預設關閉的組合元件，沒有服務啟動、公開 route、憑證發現或排程。沒有把真實研究資料／Apple 憑證交給新程式，沒有更動雲端、KMS、TestFlight 或刪帳完成標示。

## 為什麼不能只檢查目前帳號已換包

只有目前的帳號 key row 使用 V2，不代表備份也能靠 V2 恢復。若備份只留下 V1 包裝的 DEK，銷毀 V1 可能讓存活帳號失去災復能力。反過來，已關閉帳號的 V1 副本存在，也不能直接當成應保留 V1 永久使用的理由；必須分別核對已撤銷的原始證據與存活帳號的復原路徑。

新的關卡做以下核對：

1. 固定程式來源、scope、GCS 來源清冊、獨立復原位置、舊／新版本、所有狀態及稽核儲存位置，以及操作員、派送排空者、範圍覆核者三把不同簽署金鑰。
2. 從來源的目前／歷史／proposal 實體版本推導帳號集合，**不沿用先前換包批次的帳號名單**。任何實體內容找不到目前權威帳號／key row 就停止，不跳過。
3. 存活帳號必須已使用指定的新版本。實際 unwrap 目前 DEK，並對每份舊版依賴比對原始 DEK；同一 `dek_id` 但不同密碼學內容也拒絕。
4. 每個指定復原來源都必須有該存活帳號的目前新版本副本，且實際 unwrap 後與現用 DEK 相同。只存在歷史副本、缺一個帳號、仍使用舊版本或錯誤資料金鑰均停止。
5. 關帳帳號必須有原生命週期的 closing、閉鎖的 key row、原始 closure receipt 與 proposal tombstone 證據。**不重新解密關帳者的舊 DEK**。
6. 驗證前後重讀完整指定清單、版本、policy、帳號狀態及寫入 fence；觀察到變動就要求重新覆核。軟刪除未知、403／412、bucket retention 或舊依賴有 hold 都不放行。

兩輪一致仍不是全域原子快照，也無法發現未列出的電腦／離線備份。真正派送前另要求新鮮的獨立簽署，綁定精確方案、來源完整性、舊程序排空及復原位置的外部證據雜湊。這些是**受信任人員的明確聲明**，不是程式自動證明的事實；測試只驗證簽章與綁定。

## 操作與失敗回復

- **停用前**：先完成並保存完整的上述復原證據，再簽署固定方案；派送前重新盤點及實際驗證新版本／復原副本，通過才呼叫 `KeyLifecycleDispatch`。
- **排程銷毀前**：舊版已停用，不能再要求它解密。程式核對先前不可變的 DEK 比對證據、完全相同的原始物件版本，並重新實測現用與復原的新版 DEK。物件、policy、帳號或備份改變都拒絕。
- **回應遺失**：沿用低層的獨立派送排空簽章與 GET-only reconcile；不自動再停用／銷毀、不重建帳號 key row。
- **取消銷毀排程**：仍需操作員與範圍覆核簽章，但不要求故障的備份先修好。只回到 DISABLED，避免災復故障時連退出銷毀排程都被擋住。
- **重播已完成要求**：核對原回執，零新增 KMS mutation／unwrap；後來的狀態不改寫原操作結果。

清冊在兩帳號時就可能超過既有 16 KiB 單筆狀態上限，因此原始 review 以 8 KiB 分段、內容雜湊固定、最後才發布根清冊。讀取時逐段核對來源、順序、大小及整體雜湊；缺段、重排或根寫入失敗不會被當成完整證據。不放寬共用 StateStore 的上限。

## 本機驗收

新增36項測試，涵蓋舊備份、缺帳號、相同識別碼但不同DEK、舊程序晚到帳號、原始撤銷證據缺失、來源／位置／角色不符、過期與中途到期簽章、物件變動、hold／retention、分段損壞、重啟及重播。完整 Lite 測試的實際總數另見本輪固定來源報告；上述項目包含其中，不能加總。

端到端合成探針使用3個帳號、2個指定來源、37個實體版本：

| 情境 | 驗證結果 |
| --- | --- |
| 現用帳號已換包，復原來源仍舊／不完整 | 先停止，KMS變更0次 |
| 補齊復原副本後 | 2個存活帳號實際DEK核對通過，1個關閉帳號沿用原撤銷證據 |
| 停用生效但回應遺失，重啟及重播 | 額外變更0次，獨立核對後才接續 |
| 停用→排程→取消→再次排程 | 共4個明確合成要求；取消時不啟用金鑰 |
| 復原清冊暫時無法讀取 | 仍可取消銷毀排程 |
| 合成provider移除V1材料後 | 兩個存活帳號仍可讀；關帳帳號未重新開啟 |
| 原始版本／grant／稽核／額度 | 保持原樣，只有新的review及操作稽核寫入合成儲存 |

探針用真實 AES、應用程式驗證器、SQLite 與版本化 GCS 替身；Google／Apple、簽署人的外部調查及時間均為合成。31天是模擬時鐘，沒有建立刪除承諾。真實雲端呼叫與金鑰銷毀均為0。

## 真實外測前的界線

- 這是有界的本人候選驗收：盤點沿用1000筆列舉項目／2000次邏輯讀取等上限；review上限1 MiB、DEK unwrap上限512次，兩輪與解密共用300秒檢查，單一進行中的RPC仍受transport timeout約束。超出即停止，不截斷帳號或宣布完成。**大規模分區清冊與全域退休協調尚未完成**，不能把上限當成一般使用者的服務帳號上限。
- 正式部署須將IAM／命令入口限制到此組合流程；Python內部低層物件不是權限隔離邊界，不能讓任意服務呼叫銷毀。
- KMS沒有這裡可用的generation前置條件；重讀不能取代排空、唯一權限與實際transport不重試的驗收。
- 真實來源完整性、離線／異地副本、獨立人員保管、Google KMS／GCS實測與完整刪帳資料目錄仍未完成。簽署欄位為true不會讓輸出變成全域已驗證。
- 觀察到DESTROYED也不宣稱所有實體備份已清除；目前 `account_deleted`、`physical_backups_erased` 均為false，現有App仍顯示 `backup_pending`。還要驗證同帳號的全部金鑰版本、Apple撤銷及資料處置，不能只以一個舊版本退休結案。

## 參照

- Google說明輪替不會自動重新加密舊資料，也不自動停用或銷毀舊版本：[Rotate a key](https://docs.cloud.google.com/kms/docs/rotate-key)。因此必須實測復原副本，而非只讀新版本設定。
- 停用可逆，排程可恢復到停用；DESTROYED與供應者完整備份清除有不同時程：[Key version states](https://docs.cloud.google.com/kms/docs/key-states)。本輪沒有採用固定對外刪除期限。
- GCS hold會阻止物件刪除或取代：[Object holds](https://docs.cloud.google.com/storage/docs/object-holds)。本程式另採保守工程政策：觀察到受保護的舊金鑰依賴時，先阻擋退休並交由獨立處置覆核，不把KMS操作當成繞過GCS保護的方法。
